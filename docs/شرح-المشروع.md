# تفكيك تطبيق Social App: من الفكرة لطلب الشبكة

الشرح ده بيكمّل مفاهيم الأسابيع اللي بعتها، ويربط كل مفهوم بمكانه الفعلي في المشروع. الأسلوب بسيط في الكود، مع توضيح الآلية الداخلية بدل حفظ أسماء الدوال.

---

## الأسبوع الأول: البنية التحتية ومبادئ React الأساسية

### 1. تطبيق الصفحة الواحدة (SPA) وClient-Side Rendering

المتصفح بيبدأ من `index.html`. جواه `<div id="root"></div>`، وبعده بيحمّل `src/main.tsx`. الملف ده بيستدعي `createRoot` ويعرض `<App />` داخل الـroot.

التنقل من الرئيسية إلى `/profile` مش بيطلب HTML جديد لكل شاشة؛ React Router بيغيّر المكون المعروض باستخدام History API. عند فتح `/profile` مباشرة من رابط خارجي، الاستضافة لازم ترجع `index.html`، وبعدها Router يعرف الشاشة المطلوبة.

Vite بيقدّم الملفات في التطوير مع HMR، و`npm run build` بيعمل typecheck ثم bundle إنتاجي داخل `dist`. الـbundle بيضم JavaScript وCSS؛ الصور المنشورة نفسها بتيجي من الـAPI.

### 2. المكونات (Component-Driven Architecture)

`PostCard` مسؤول عن منشور واحد، و`Comments` مسؤول عن تعليقات المنشور، و`Avatar` بيعرض صورة المستخدم. `Feed` بيجلب القائمة ويرسم كل عنصر بـ `.map()`.

```tsx
{
  list.items.map((post) => (
    <PostCard key={post._id} post={post} onDeleted={remove} />
  ));
}
```

الفصل ده بيمنع تكرار كود المنشور في الرئيسية، الملف الشخصي، المحفوظات، وتفاصيل المنشور. البطاقات نفسها بتتستخدم في الشاشات الأربع.

### 3. JSX والـVirtual DOM

JSX بيتحوّل أثناء البناء لتعليمات JavaScript من خلال JSX runtime. مش لازم يتحول حرفياً لـ`React.createElement` في إعدادات React الحديثة. بنكتب `className` و`onClick` بدل `class` و`onclick`.

عند `setState`، React بيحسب التمثيل الجديد للواجهة، ويقارن الهوية والنوع والمفاتيح قبل تحديث DOM. ده مش معناه إن كل تغيير بيعيد بناء الصفحة كلها أو إن الـVirtual DOM أسرع في كل حالة.

`StrictMode` موجود في `main.tsx`. في التطوير بيكرر بعض خطوات التصيير وتشغيل/تنظيف Effects للكشف عن الأخطاء؛ عشان كده بنهتم بـCleanup، وما بننشرش بوست من داخل Effect عند Mount.

## الأسبوع الثاني: الحالة والخصائص وديناميكية البيانات

### 1. Props وتدفق البيانات أحادي الاتجاه

`Feed` يمرّر `post` إلى `PostCard`. البطاقة بتستخدم البيانات، ومش بتعدل كائن الأب مباشرة. لو حذفنا المنشور، البطاقة تنادي callback `onDeleted(postId)`، والأب يعدّل قائمته.

`Modal` يستقبل `children`. ده Composition: نفس الإطار بيحتوي نموذج تعديل، رسالة تأكيد، قائمة معجبين، أو مشاركة، من غير نسخ نافذة جديدة لكل وظيفة.

### 2. useState، الـImmutability والـFunctional Updater

في `Auth.tsx`، كل قيمة نموذج مربوطة بـ`value` و`onChange`، وده Controlled Component. القيمة المعروضة جاية من State.

```tsx
onChange={e => setValues(prev => ({ ...prev, name: e.target.value }))}
```

`prev` بيقرأ آخر حالة متاحة للتحديث، بدل الاعتماد على نسخة قديمة في closure. الـspread بيعمل كائن جديد ويغيّر خاصية واحدة. تعديل `values.name` مباشرة مش كفاية لإخطار React.

نفس الفكرة في حذف عنصر من القائمة:

```tsx
list.setData((prev) => ({
  ...prev,
  items: prev.items.filter((item) => item._id !== id),
}));
```

React بيجمع تحديثات عديدة (Batching). ترتيب الأحداث والاعتماد على حالة سابقة سبب أساسي لاستخدام updater في القوائم والعدادات.

### 3. الأحداث والرندرة الشرطية والمفاتيح

`onClick={() => setModal("edit")}` بيخزن دالة للحدث؛ `onClick={setModal("edit")}` ينفّذ التعديل أثناء التصيير وده خطأ.

`key={post._id}` ثابت حتى لو ترتيب المنشورات اتغير. استخدام index هنا ممكن يربط حالة تعليق مفتوح بمنشور مختلف بعد إضافة أو حذف عنصر.

الحالات الثلاث في `Feed`: تحميل، خطأ، نجاح. داخل النجاح بنفرّق بين قائمة فاضية وقائمة فيها بيانات. فشل الطلب مش بيتعرض كأنه «مفيش منشورات».

## الأسبوع الثالث: دورة الحياة والتأثيرات والتوجيه المتقدم

### 1. useEffect وAbortController

`hooks/useCollection.ts` بيحمّل صفحة عناصر عند تغيّر `loader` أو `page` أو رقم التحديث. `hooks/useResource.ts` بيعمل نفس الدورة لعنصر واحد.

```tsx
useEffect(() => {
  const controller = new AbortController();
  // load() يستدعي loader(page, controller.signal)
  return () => controller.abort();
}, [loader, page, version]);
```

لو المستخدم انتقل بسرعة، Cleanup يلغي الطلب القديم. كمان بنفحص `signal.aborted` قبل تحديث State، عشان Response متأخر ما يكتبش بيانات الصفحة القديمة فوق الجديدة.

`AbortError` بيتحافظ عليه في `services/api.ts`، ومش بيتحول لرسالة «الإنترنت فصل». الإلغاء الطبيعي مختلف عن فشل الشبكة.

### 2. تثبيت الـLoader بـuseCallback

```tsx
const loader = useCallback(
  (page, signal) => postService.userPosts(target, page, signal),
  [target]
);
```

لو الدالة اتعملت من جديد في كل render، Effect المعتمد عليها ممكن يعيد الطلب باستمرار. تثبيت المرجع بيخلي التغيير مرتبطاً فعلاً بـ`target`.

### 3. المسارات المتداخلة وOutlet

`App.tsx` يبني Router مرة واحدة خارج المكون. `ProtectedRoute` فوق `Layout`. `Layout` فيه Header وSidebar و`Outlet`؛ الجزء المتغيّر هو محتوى العمود الأوسط.

`useParams` بيقرأ `postId` في `/posts/:postId` و`userId` في `/users/:userId`. `useSearchParams` في Feed بيحفظ `tab=following` و`images=true` في الرابط. تغيير الفلتر بيرجع صفحة النتائج للأولى.

بعد الدخول، `useNavigate` بيرجع للمسار اللي المستخدم حاول يفتحه. إحنا بنقبل مسار داخلي يبدأ بـ`/`، ونرفض `//` عشان ما نعملش انتقال لعنوان خارجي.

## الأسبوع الرابع: المعمارية والمصادقة وطبقة الخدمات

### 1. توزيع المسؤوليات

| الطبقة     | المسؤولية                       | مثال                |
| ---------- | ------------------------------- | ------------------- |
| pages      | تجميع الشاشة ومصدر بياناتها     | Feed، Profile       |
| components | عرض/تفاعل قابل لإعادة الاستخدام | PostCard، MediaForm |
| services   | URLs، methods، payload، errors  | api.ts، social.ts   |
| context    | حالة المستخدم المشتركة          | AuthContext         |
| hooks      | دورة جلب بيانات مع Cleanup      | useCollection       |
| types      | شكل البيانات أثناء التطوير      | User، Post، Comment |

TypeScript يساعد في أخطاء شكل البيانات أثناء التطوير؛ مش بيضمن وحده إن Response خارجي صحيح في Runtime. طبقة الشبكة بتفحص HTTP status و`success` ووجود `data` قبل استخدام الرد.

### 2. Authentication Flow خطوة بخطوة

1. نموذج التسجيل أو الدخول يجمع القيم ويمرّرها لـZod في `services/validation.ts`.
2. `authService` يرسل JSON إلى `/users/signup` أو `/users/signin` بدون توكن قديم.
3. `setSession` يحفظ `data.token` في `localStorage` تحت `social-app-token`، ويحفظ المستخدم في Context.
4. `ProtectedRoute` يعرض `Outlet` للمستخدم أو يعيد الزائر إلى `/login`.
5. عند Reload، `AuthProvider` يقرأ التوكن ويطلب `/users/profile-data` للتحقق من الجلسة وجلب البيانات الكاملة.
6. طلب محمي يرجع 401 يطلق `auth-expired`؛ Provider يمسح الجلسة ويرجع المستخدم للدخول.

في تغيير كلمة السر، الخادم بيرجع توكن جديد. بنستبدله مباشرة عشان الطلبات اللي بعد كده تستخدم الجلسة الصحيحة.

### 3. عقد الاستجابة الحقيقي (Response Contract)

الخادم بيرجع:

```json
{
  "success": true,
  "message": "success",
  "data": { "posts": [] },
  "meta": { "pagination": { "currentPage": 1, "numberOfPages": 1 } }
}
```

المهم هنا إن البيانات داخل `data`، مش في الجذر. المحفوظات اسمها `data.bookmarks`، والاقتراحات `data.suggestions`. جلب القوائم بيحوّلها في الخدمة إلى `{ items, pagination }` عشان Hook ما يحتاجش يعرف اسم كل endpoint.

### 4. JSON مقابل Multipart FormData

الدخول وتغيير كلمة السر والمشاركة JSON. المنشورات والتعليقات والردود Multipart عشان تدعم الملفات.

```tsx
const form = new FormData();
form.set("body", text.trim());
if (image) form.set("image", image);
```

ما بنحددش `Content-Type: multipart/form-data` بنفسنا. المتصفح لازم يضيف الـboundary اللي بيقسم أجزاء الطلب. الصورة الشخصية بتستخدم اسم الحقل `photo`، مش `image`.

فحص نوع/حجم الصورة عندنا لتحسين التجربة، والخادم يظل مسؤولاً عن الفحص الحقيقي. `MediaForm` بيعمل معاينة بـ`URL.createObjectURL` وينظفها بـ`URL.revokeObjectURL`.

### 5. حدود الحماية

حماية المسار وإخفاء زر تعديل منشور الغير جزء من تجربة الواجهة. التحقق النهائي من ملكية المنشور وصلاحية التوكن مسؤولية الخادم. حفظ JWT في localStorage حسب المنهج والـAPI الحالي يجعل الحماية من XSS مهمة؛ إحنا بنعرض النصوص عبر React escaping من غير `dangerouslySetInnerHTML`.

## الأسبوع الخامس: CRUD والتفاعلات وتجربة الاستخدام

### 1. CRUD المنشورات والتعليقات

`Composer` ينشئ منشوراً ثم يحدّث أول صفحة من القائمة. `PostCard` يعدّل بيانات بطاقته بعد نجاح PUT. الحذف يخفي البطاقة فوراً، ويرجعها لو DELETE فشل؛ بعدها يبلغ الأب بالحذف الناجح.

التعليق أو الرد الجديد بيتضاف للمصفوفة محلياً باستخدام `[...prev.items, item]`. مش بنعيد تحميل Feed بالكامل مع كل تعليق. تعديل وحذف التعليق بيحدث نفس القائمة. عداد الردود مرتبط بمكون التعليق الأب، وعداد التعليقات مرتبط ببطاقة المنشور.

### 2. Optimistic UI وRollback

في الإعجاب والحفظ والمتابعة، الواجهة تتغير قبل Response، لكن التغيير مش بيتعتبر مؤكداً لحد ما الخادم يوافق. بنحفظ الحالة السابقة ونرجع لها عند الفشل.

زر الإعجاب/الحفظ بيتقفل وقت الطلب عشان الضغط السريع ما يعملش toggle مزدوج أو rollback لنسخة أقدم. قيمة العداد النهائية بتيجي من الخادم، وما بنكتفيش بتخمين محلي.

### 3. إعجابات، مشاركة، إشارات ومتابعة

`hasLiked` بيقبل معرفات المستخدمين سواء strings أو objects. `LikesList` يجلب قائمة المعجبين بصفحات.

اختبار الخادم أثبت إنه يرفض مشاركة بنص `""`، لكنه يقبل `" "` للمشاركة بدون تعليق إضافي؛ الخدمة بتتعامل مع الحالة دي. ولو نفس الحساب شارك نفس المنشور تاني، الخادم يرجع 409، ورسالة عربية بتظهر داخل نافذة المشاركة.

`RichText` بيلوّن `@username` كنص آمن؛ الخادم هو اللي بيحدد المستخدم ويولّد إشعار الإشارة. مفيش endpoint للبحث عن username في التوثيق، لذلك ما عملناش autocomplete غير حقيقي.

المتابعة في `UserCard` تستخدم حالة تفاؤلية مؤقتة ثم تعيد جلب بيانات المستخدم الحالي. ده يخلي أزرار المتابعة في أجزاء مختلفة من الصفحة تتفق مع بعضها.

### 4. الإشعارات ودورة التنظيف

`Layout` يطلب عداد غير المقروء كل 60 ثانية. Cleanup يوقف interval ويلغي الطلب عند الخروج. حدث `notifications-changed` بيحدّث العداد فور تحديد إشعار كمقروء.

أنواع الإشعارات الفعلية بتشمل `like_post` و`follow_user`. الوصول للتفاعل يعتمد على `entityType` و`entity`؛ لو الكيان تعليق، بنستخرج منشوره قبل بناء الرابط.

### 5. التصميم وحالات الواجهة

ألوان التصميم الأساسية `#00298d` و`#1877f2` و`#f0f2f5`. اللمسة الخاصة هي العلامة النصية Social، الخط العربي Tajawal، الرسائل القريبة من المستخدم، ونمط الحكايات في الدخول والبطاقات.

على الكمبيوتر فيه ثلاثة أعمدة. في الشاشات المتوسطة بيختفي عمود الاقتراحات، وعلى الموبايل فيه عمود واحد وBottom Navigation. النوافذ تستخدم `<dialog>` عشان الـfocus والحركة بـTab والإغلاق بـEscape، مع إعادة التركيز للعنصر السابق.

## ترتيب قراءة الكود والتجربة العملية

ابدأ بـ`main.tsx` ثم `App.tsx`، وبعدهم `AuthProvider` و`services/api.ts`. اقرأ `Feed` مع `useCollection`، وبعدها `PostCard` و`Comments`. أخيراً راجع `Profile` و`Notifications` و`Settings`.

جرّب: تسجيل → نشر → تعديل → إعجاب → تعليق → رد → حفظ → مشاركة → فتح الملف الشخصي → خروج. افتح Network في DevTools واربط كل ضغطة بالطريقة والمسار والـpayload في `docs/api-map.md`.

`npm test` بيختبر 14 حالة في طبقة الخدمات، و`npm run verify:api` بيختبر الخادم فعلياً بحسابات QA مستقلة. التقرير بيفصل نجاح الشبكة عن مراجعة شكل الواجهة في المتصفح.
